CKAD Warm-Up Practical Exam (Apply-Ready)

Welcome back to Kubernetes! This gentle, 12-task warm-up exam is designed to help you shake off the rust with kubectl imperative commands, YAML generation (--dry-run=client -o yaml), and kubectl apply.

  • Difficulty: Easy / Warm-Up
  • Target Time: ~45–60 minutes
  • Prerequisites: Any Kubernetes cluster (kind, minikube, k3s, Docker Desktop, etc.) and kubectl.

Pre-Flight Setup

  1. Set up the same speed aliases you would use on the real CKAD exam:
    bash
    alias k=kubectl
export do="--dry-run=client -o yaml"
  2. Apply the starter environment (creates the ckad-warmup namespace plus two helper Deployments/Services used in later tasks):
    bash
    kubectl apply -f setup.yaml
  3. Verify the setup is ready:
    bash
    kubectl get all -n ckad-warmup

Tip: Put all your created manifests in warmup-exam/ (or /tmp/opencode/) and apply them with kubectl apply -f <file>.yaml. Don't peek at the Solutions until you try each task!

Task 2: Pod with Command, Args & Resource Requests/Limits (Weight: 8%)

In namespace ckad-warmup, create a Pod named sleeper:

  • Image: busybox:1.36
  • Command: ["sh", "-c", "echo Warming up && sleep 3600"]
  • Resource requests: cpu: 50m, memory: 64Mi
  • Resource limits: cpu: 100m, memory: 128Mi
  • Check what QoS Class Kubernetes assigned to sleeper.
Hint

Start from k run sleeper -n ckad-warmup --image=busybox:1.36 $do -- sh -c "echo Warming up && sleep 3600" > task2-sleeper.yaml and edit resources. Check QoS with kubectl get pod sleeper -n ckad-warmup -o jsonpath='{.status.qosClass}'.

Solution & Verify (Task 2)

task2-sleeper.yaml:

yaml
apiVersion: v1
kind: Pod
metadata:
  name: sleeper
  namespace: ckad-warmup
spec:
  containers:
  - name: sleeper
    image: busybox:1.36
    command: ["sh", "-c", "echo Warming up && sleep 3600"]
    resources:
      requests:
        cpu: 50m
        memory: 64Mi
      limits:
        cpu: 100m
        memory: 128Mi
bash
kubectl apply -f task2-sleeper.yaml

Verify: kubectl get pod sleeper -n ckad-warmup -o jsonpath='{.status.qosClass}{"\n"}' -> Burstable

Task 3: ConfigMap — Env Var & Volume Mount (Weight: 10%)

In namespace ckad-warmup:

  1. Create a ConfigMap named app-settings with two literal keys:
    • APP_ENV=staging
    • LOG_LEVEL=debug
  2. Create a Pod named config-pod using image busybox:1.36 running sleep 3600:
    • Load APP_ENV as an environment variable inside the container.
    • Mount the entire app-settings ConfigMap as a volume at /etc/config.
Hint

Create the ConfigMap imperatively with kubectl create configmap app-settings -n ckad-warmup --from-literal=APP_ENV=staging --from-literal=LOG_LEVEL=debug, then add env (valueFrom.configMapKeyRef) and volumes/volumeMounts to the Pod YAML.

Solution & Verify (Task 3)
bash
kubectl create configmap app-settings -n ckad-warmup --from-literal=APP_ENV=staging --from-literal=LOG_LEVEL=debug

task3-config-pod.yaml:

yaml
apiVersion: v1
kind: Pod
metadata:
  name: config-pod
  namespace: ckad-warmup
spec:
  containers:
  - name: config-pod
    image: busybox:1.36
    command: ["sleep", "3600"]
    env:
    - name: APP_ENV
      valueFrom:
        configMapKeyRef:
          name: app-settings
          key: APP_ENV
    volumeMounts:
    - name: config-vol
      mountPath: /etc/config
  volumes:
  - name: config-vol
    configMap:
      name: app-settings
bash
kubectl apply -f task3-config-pod.yaml

Verify:

bash
kubectl exec config-pod -n ckad-warmup -- printenv APP_ENV
kubectl exec config-pod -n ckad-warmup -- ls /etc/config

Task 5: Multi-Container Pod (Sidecar + emptyDir) (Weight: 10%)

In namespace ckad-warmup, create a Pod named logger-pod with two containers sharing an emptyDir volume named log-vol:

  1. Container writer (busybox:1.36): mounts log-vol at /var/log and runs: sh -c "while true; do date >> /var/log/app.log; sleep 5; done"
  2. Container sidecar (busybox:1.36): mounts log-vol at /var/log and runs: sh -c "tail -n+1 -f /var/log/app.log"
Hint

Generate a single-container Pod YAML with $do, duplicate the container block for sidecar, add emptyDir: {} under volumes, and mount it in both containers. Test with kubectl logs logger-pod -n ckad-warmup -c sidecar.

Solution & Verify (Task 5)

task5-logger-pod.yaml:

yaml
apiVersion: v1
kind: Pod
metadata:
  name: logger-pod
  namespace: ckad-warmup
spec:
  containers:
  - name: writer
    image: busybox:1.36
    command: ["sh", "-c", "while true; do date >> /var/log/app.log; sleep 5; done"]
    volumeMounts:
    - name: log-vol
      mountPath: /var/log
  - name: sidecar
    image: busybox:1.36
    command: ["sh", "-c", "tail -n+1 -f /var/log/app.log"]
    volumeMounts:
    - name: log-vol
      mountPath: /var/log
  volumes:
  - name: log-vol
    emptyDir: {}
bash
kubectl apply -f task5-logger-pod.yaml

Verify: kubectl logs logger-pod -n ckad-warmup -c sidecar

Task 6: Deployment, Scaling, Rolling Update & Rollback (Weight: 10%)

In namespace ckad-warmup:

  1. Create a Deployment named api-deploy with image nginx:1.25-alpine and 2 replicas.
  2. Scale api-deploy to 3 replicas.
  3. Update the container image to nginx:1.26-alpine and wait for the rollout to finish.
  4. Check the rollout history, then roll back api-deploy to the previous revision (nginx:1.25-alpine).
Hint

Use kubectl create deployment, kubectl scale, kubectl set image, kubectl rollout status, kubectl rollout history, and kubectl rollout undo.

Solution & Verify (Task 6)
bash
kubectl create deployment api-deploy -n ckad-warmup --image=nginx:1.25-alpine --replicas=2
kubectl scale deployment api-deploy -n ckad-warmup --replicas=3
kubectl set image deployment/api-deploy -n ckad-warmup nginx=nginx:1.26-alpine
kubectl rollout status deployment/api-deploy -n ckad-warmup
kubectl rollout history deployment/api-deploy -n ckad-warmup
kubectl rollout undo deployment/api-deploy -n ckad-warmup

Verify: kubectl get deploy api-deploy -n ckad-warmup -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}' -> nginx:1.25-alpine

Task 7: Readiness & Liveness Probes (Weight: 8%)

In namespace ckad-warmup, create a Pod named probe-web (nginx:1.25-alpine, port 80) with:

  • A readinessProbe doing an HTTP GET on / port 80 (initialDelaySeconds: 2, periodSeconds: 5).
  • A livenessProbe doing an HTTP GET on / port 80 (initialDelaySeconds: 5, periodSeconds: 10).
Hint

Generate probe-web YAML with $do, then add readinessProbe and livenessProbe with httpGet: { path: /, port: 80 }.

Solution & Verify (Task 7)

task7-probe-web.yaml:

yaml
apiVersion: v1
kind: Pod
metadata:
  name: probe-web
  namespace: ckad-warmup
spec:
  containers:
  - name: probe-web
    image: nginx:1.25-alpine
    ports:
    - containerPort: 80
    readinessProbe:
      httpGet:
        path: /
        port: 80
      initialDelaySeconds: 2
      periodSeconds: 5
    livenessProbe:
      httpGet:
        path: /
        port: 80
      initialDelaySeconds: 5
      periodSeconds: 10
bash
kubectl apply -f task7-probe-web.yaml

Verify: kubectl describe pod probe-web -n ckad-warmup | grep -E "Liveness|Readiness"

Task 8: Job & CronJob (Weight: 8%)

In namespace ckad-warmup:

  1. Create a Job named batch-job using busybox:1.36 that runs echo "Job complete" with completions: 2 and parallelism: 2.
  2. Create a CronJob named heartbeat using busybox:1.36 that runs date every 5 minutes (*/5 * * * *).
Hint

Use kubectl create job batch-job -n ckad-warmup --image=busybox:1.36 $do -- echo "Job complete" and add completions: 2 / parallelism: 2 under spec. Use kubectl create cronjob heartbeat -n ckad-warmup --image=busybox:1.36 --schedule="*/5 * * * *" -- date.

Solution & Verify (Task 8)

task8-batch-job.yaml:

yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: batch-job
  namespace: ckad-warmup
spec:
  completions: 2
  parallelism: 2
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: batch-job
        image: busybox:1.36
        command: ["echo", "Job complete"]

Task 9: Troubleshoot & Fix a Broken Service (Weight: 8%)

In namespace ckad-warmup, setup.yaml already created a Deployment broken-app and a Service broken-svc.

  1. Check why broken-svc has no endpoints (kubectl get endpoints broken-svc -n ckad-warmup).
  2. Fix broken-svc so it properly routes traffic to the broken-app Pods.
Hint

Compare kubectl get pods -n ckad-warmup --show-labels against kubectl describe svc broken-svc -n ckad-warmup. Edit the Service selector (app: broken-apps -> app: broken-app).

Solution & Verify (Task 9)

The Service broken-svc has selector.app: broken-apps, while the Pods have app: broken-app.

bash

# (Or run: kubectl edit svc broken-svc -n ckad-warmup)

Verify: kubectl get endpoints broken-svc -n ckad-warmup (should now list 2 Pod IP endpoints!)

Task 12: Basic NetworkPolicy (Weight: 8%)

In namespace ckad-warmup, setup.yaml deployed an api-server Pod with label app: api. Create a NetworkPolicy named allow-web-to-api that:

  • Selects Pods with label app: api.
  • Allows Ingress on TCP port 80 only from Pods in the same namespace with label app: web.

(Note: Some minimal local clusters like Docker Desktop/kind without Calico/Cilium accept the NetworkPolicy object even if they don't enforce it—still great practice writing and applying the YAML!)

Hint

Set spec.podSelector.matchLabels.app: api, policyTypes: ["Ingress"], and an ingress rule with from: [{ podSelector: { matchLabels: { app: web } } }] and ports: [{ protocol: TCP, port: 80 }].

Solution & Verify (Task 12)

task12-netpol.yaml:

yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-api
  namespace: ckad-warmup
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: web
    ports:
    - protocol: TCP
      port: 80
bash
kubectl apply -f task12-netpol.yaml

Verify: kubectl describe networkpolicy allow-web-to-api -n ckad-warmup
